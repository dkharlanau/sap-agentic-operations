SAO deliberately does not assume that the latest successful message belongs to the latest authoritative change.

Why it exists

Support incidents become dangerous when teams optimize for the technical symptom: reprocess an IDoc, overwrite a target value, retry a job. The harder question is whether the evidence actually justifies that action for the current business change.

01

Bound the diagnosis

Resolve identity, authority, change/message causality, mapping version, transport state, and target observation before jumping to a fix.

02

Show evidence gaps

A missing current outbound event or stale target observation becomes an explicit diagnostic, not an excuse for plausible inference.

03

Block unsafe shortcuts

The analyzer can state which recovery actions are not justified and define the business-level postcondition that would count as resolved.

Start from the evidence you can export

The practical alpha works locally without SAP credentials, a database, or an LLM. It is designed for the exports, incident lists, and operational artifacts support teams can often obtain.

Full incident path

sao incident init ./incident \
  --incident-id INC-001 \
  --object-type customer \
  --source-id C-100 --target-id BP-501 \
  --authority-system MDG \
  --attribute delivery_control

sao incident validate ./incident
sao incident analyze ./incident

Fast Excel-style triage

sao quickcheck analyze my-incidents.csv converts each row into the same in-memory Evidence Pack semantics, making it useful for AMS lists, replication backlogs, cutover validation spreadsheets, and message triage.

Not autonomous SAP administration. The current product is evidence-first diagnosis and bounded recovery guidance; any real write action needs explicit policy, authorization, and a verifiable business postcondition.

Where it connects

SAO is the operational edge of the toolkit: it consumes observable state and can feed structured evidence back into data assurance, cutover, and project governance.

Reconciliation as Code →Use systematic data checks when incident resolution depends on target correctness.Cutover Graph →Surface operational blockers and recovery state during a cutover window.Project Evidence Graph →Preserve diagnosis and postcondition evidence as part of release rationale.
Agent entry point

Agentic does not mean unconstrained.

The safest useful agent is one that can explain what it knows, what it does not know, and which actions current evidence does or does not justify. SAO exposes that reasoning surface before execution.

DISCOVER

Read the capability manifest

agent-manifest.json separates diagnosis, validation, and suggested recovery from unrestricted writes.

EVIDENCE

Require causal support

Do not bind a message to a business change just because timestamps or IDs look close.

RECOVER

Prove the postcondition

A suggested action is incomplete until the target business state can be observed and checked after recovery.
